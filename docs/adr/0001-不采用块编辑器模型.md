# ADR 0001：不采用块编辑器模型

- 状态：已接受
- 日期：2026-11-12
- 相关：0002、0003

## 背景

Notion 与飞书文档都采用「一切皆块」的结构化数据模型（block tree），Markdown 只是输入快捷方式与导入导出格式。块模型在多人协同、块级拖拽 / 嵌套、段落级评论、数据库视图上明显优于传统富文本。

纸间笔记是**个人、单机、本地优先**的笔记应用，需要考虑是否跟进这一架构。

## 决定

**不采用块模型。** 保留「每篇笔记一段 `content` 字符串 + `mode` 标记」的模型，配合 HTML 富文本与 Markdown 双模式。

## 理由

1. 块模型的收益几乎全部依赖云端与多人协作：协同粒度、块级记录、数据库视图、跨文档引用。纸间笔记是单机应用，这些收益为零。
2. 块 JSON 是私有 schema。用户换工具时仍要导出，而导出必然丢块类型（Notion 的 callout 只能导出成 HTML、折叠块退化成缩进、数据库导出成 CSV）。这与「数据自己掌握」的核心前提冲突。
3. 改造范围是整个应用：编辑器、存储、搜索、导入导出、剪藏、迁移全部重写，收益却不在本产品的目标里。
4. 值得借鉴的是**输入体验**（`# ` 变标题、`/ ` 命令面板、块拖拽），这些可以在现有编辑器上补，不需要改变存储格式。

## 后果

- 做不到段落级评论、块级实时协同、内嵌数据库视图。
- 富文本编辑能力受限于 WebView 的 `contenteditable`，Word 级分栏 / 修订不在范围内。
- 但笔记始终是普通文本，能被 git / grep / 任何编辑器直接处理。

## 什么时候重新评估

只有当产品目标变成「多人实时协作的团队知识库」时。那会是另一个产品，而不是给纸间笔记加一个协同功能。

## 备选

- 引入 BlockSuite / ProseMirror 做块模型：能力强，但引入私有文档 schema 与大量依赖，违背本地优先前提。
- 只把 UI 做成块样式而底层仍存 HTML：徒增复杂度，没有块模型的实际收益。
