# ADR 0005：重新评估「Markdown 编辑」的定位

- 状态：**已接受（路线 A）** · 2026-11-12 用户拍板
- 日期：2026-11-12
- 相关：0002、0003

## 触发

v1.0 实际使用后反馈：Markdown 模式下待办渲染错、图片上传不对，并问「能不能参考 Obsidian 或飞书」「Markdown 编辑是否还有必要存在」。

## 先把两件事拆开

| | 内容 | 是否需要 |
| --- | --- | --- |
| ① Markdown 作为**存储与交换格式** | `notes/*.md` 镜像、导入导出、ENEX、git / grep、换软件不丢 | **必须保留**，这是 ADR 0002 的核心承诺 |
| ② Markdown 作为**编辑界面**（裸 textarea + 右侧静态预览） | 当前实现，用户直接面对 `##`、`- [ ]`、`![](data:…)` | **存疑**，本 ADR 讨论的就是它 |

两者没有绑定关系。Obsidian 的 Live Preview 正是反例：用户看见的是渲染后的标题、可点击的复选框和图片，磁盘上仍是纯 `.md`。**"数据自己掌握"不等于"必须看着符号打字"。**

## 当前实现暴露的问题（本轮实测）

- `marked` 已把 `- [x]` 渲染成 `<li><input type="checkbox">`，但项目符号没去掉 → 圆点与复选框并存；项目里旧的 `renderTasks` 想自己替换 `[x]`，实际从未匹配上。
- 工具栏会在已有待办行上叠加出 `- [ ] - [ ]`；复选框是 `disabled`，不能点。
- 图片把整段 base64 塞进 textarea；文件 MIME 为空时被降级成「仅附件」，根本没插进正文。
- 左右分栏把「写」和「结果」割裂；中文 IME、光标位置、表格 / 图片 / 待办等块级对象都要自己再实现一遍渲染规则，每加一种语法就多一处维护点。

**判断：这个源码 textarea 承担了 Markdown 的全部缺点，却没有带来额外好处**——纯文本落盘的价值由 `.md` 镜像承载，与用户以什么方式打字无关。作为与富文本对等的一等公民，性价比不成立。

## 三档路线

| 路线 | 做法 | 成本 | 效果 |
| --- | --- | --- | --- |
| **A（推荐）** | 保留单一所见即所得编辑器；Markdown **降级为「源码视图」**，收进更多菜单；新笔记默认富文本；落盘仍生成 `.html` 主档 + `.md` 镜像（turndown 转换） | 中：改默认模式、入口位置、镜像生成规则 | 日常不碰符号，纯文本承诺不破，维护面从两套编辑器收敛到一套 |
| **B** | 上 CodeMirror 6 Live Preview（Obsidian 路线）：源码行内渲染标题 / 复选框 / 图片，磁盘仍是 `.md` | 高：引入 CodeMirror、重写编辑器、处理中文 IME 与光标、维护装饰层 | 体验最好，但要把 Markdown 每种块都实现一遍，长期最重 |
| **C** | 保留现状，只修缺陷，把 Markdown 标注为「高级 / 源码」 | 低（本轮已做） | 不再出错，但割裂感仍在 |

## 第一版动作（路线 C，修缺陷，不改架构）

- 修待办渲染、禁止前缀叠加、预览复选框可点击并回写源码的 `[ ]` / `[x]`。
- 图片与附件改为短引用 `zhijian-attachment:<id>`，源码不再塞 base64；预览、导出、落盘镜像统一还原成自包含 data URL。
- 支持自定义数据目录、栏宽拖拽。
- **不改默认模式、不删 Markdown 模式、不动 ADR 0003 的单一真相模型**——架构变更需要用户明确拍板。

这些修复不会白做：即使按路线 A 降级为「源码视图」，它仍然要能正确渲染，`.md` 镜像也要能正确还原图片。

## 建议（已采纳）

**选 A。** 它是唯一同时满足「数据自己掌握」与「不用看符号」的方案，并把维护面收敛到一套编辑器。B 的额外收益主要面向「就是想写源码」的重度用户，对本项目当前规模不划算；若将来真要服务这类用户，在 A 之上补一个 CodeMirror 源码视图也不迟。
